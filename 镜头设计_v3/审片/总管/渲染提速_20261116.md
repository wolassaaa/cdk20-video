# 渲染提速与 Blender 5.3 试用（11-16）

HKBU SCIE1007 课程作业的科普视频（英文，讲 Ren et al. 2023 的公开案例，不是科研）。这一页是渲染工具的说明：快速渲染模板怎么用，以及几种渲染方式的速度和画质对比。不改正在出的成片。

## 1. 用法（现在就能用）

模板：`镜头设计_v3/styleframes/art/fusion/s1/inserts/fast_render.py`。用系统 Python 调用，它自己去开 Blender。

```bash
FR="D:/。hkbu/molecular science/镜头设计_v3/styleframes/art/fusion/s1/inserts/fast_render.py"
# 正式档，Cycles，Blender 5.3，帧 0–929，显卡吃不满时自动开第二路
python "$FR" 场景.blend --out 输出目录 --f0 0 --f1 929 --blender G:/software/blender-5.3/blender.exe
# 预览档（半分辨率，Cycles 8 采样 / EEVEE 16）
python "$FR" 场景.blend --out 输出目录 --f0 0 --f1 929 --profile preview
# EEVEE
python "$FR" 场景.blend --out 输出目录 --engine eevee
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--engine cycles/eevee` | cycles | 同一个 .blend 直接切换 |
| `--profile final/preview` | final | final：100% 分辨率，Cycles 用场景里的采样（没设就 24），EEVEE 64；preview：50%，Cycles 8 / EEVEE 16 |
| `--samples N`、`--pct P` | — | 覆盖采样数、分辨率百分比 |
| `--blender` | D:/software/tools/blender.exe（5.1.2） | 5.3 在 G:/software/blender-5.3/blender.exe |
| `--split auto/1/2` | auto | auto：第一帧出图后看 25 秒显卡占用，平均低于 70%、机器上只有这一个 Blender、而且 GPU 槽还空着，才开第二路 |
| `--no-bake`、`--rebake` | 烘焙开 | 关掉烘焙，或强制重烘 |

输出：`输出目录/f_0000.png …`，另有 `_way1.log`、`_way2.log`，以及 `_fast_render.json`（每路用时、秒/帧、显卡占用、等槽时间）。已经出了的帧会跳过，所以中断后重跑同一条命令就是续渲。

它做的事：
1. **烘焙**：在帧段里抽 16 帧比较几何，找出几何在变的物体（shape key、修改器、几何节点、曲线 bevel 生长、字），把这些物体烘成一个 Alembic，再换成 Mesh Sequence Cache 读取，另存为 `baked.blend`。缓存放在 `G:/cdk20/work/fast_render/`，可以用环境变量 `FAST_RENDER_CACHE` 改位置。物体的移动、旋转、显隐还用原来的关键帧。
2. **整段一次渲**：`blender -b baked.blend -P fast_render.py -s f0 -e f1 -a`，打开 persistent_data，不再每帧调一次 `render(write_still)`。
3. **两路**：两个 Blender 渲同一个帧段，靠占位文件（不覆盖 + placeholder）各自领帧。GPU 槽和 `styleframes/art/gpu_slot.sh` 共用同一组（`.slots/1`、`.slots/2`），所以全机最多两个 Blender；槽都占着时就排队等。

接入要求：
- **场景得先存成 .blend。** 现在不少脚本是在内存里建好场景、逐帧渲染。接入时先用它们的 `build` 模式存一份 .blend，或者用 `blender -b -P inserts/fast_render_build.py -- 镜头脚本.py 输出.blend`：它执行镜头脚本但不跑 main()，调用 build() 后另存。
- **注意：样板 A 存成 .blend 再渲，和内存里直接渲的画面不一样。** 底模上的药格和钞票格会多出一圈轮廓，第 445 帧平均差 24/255。用 5.1.2 照旧方式逐帧渲这份 .blend，结果和模板出的一致（差 0.36），所以差别来自"存盘"这一步，和模板无关。比较可能的原因是 `mold_kit_v1.Plate.build` 手工拼网格，加的 `pocket`/`runner` 点属性在存盘读回后有变化，这一点还没查实。样板 A 改用模板之前，要先确认哪一版是想要的画面。
- Alembic 在 Windows 上读不了带中文或全角字符的路径（能写出来，读回来是空的），所以缓存一律放在纯 ASCII 目录。
- 导出器会跳过隐藏的物体，所以烘焙时会暂时静音显隐关键帧，导出完再恢复。

## 3. 对比测试（还没测完）

测试段是样板 A 的第 420–479 帧（钞票落下、"$2.8" 长出），1080p，Cycles 24 采样，OptiX 降噪，开运动模糊。场景用 `fast_render_build.py` 从当前脚本存成 `G:/cdk20/work/speedtest/src/s108_fresh.blend`，每种方式都只开一路。

目前能下的结论：
- **慢的根源是"渲存好的 .blend 时逐帧调用 render(write_still)"，同一个文件逐帧调要 24.5 秒/帧。** 改成整段 `-a`，同一份文件在显卡被别人占着的情况下也只要 1.2–1.6 秒/帧，快了大约 15–20 倍。上面说的"7 秒/帧"走的就是这条慢路。旧脚本在内存里建好场景后逐帧渲，本来就快（约 0.8–1.0 秒/帧），这时候换模板主要是换来续渲和两路，速度差不多。
- 样板 A 这一段里，几何在动的物体只有 3 个（bill_6、bill_7、letter_5），所以烘不烘焙速度差不多（F 和 C 一样）。烘焙在几何节点或 shape key 很重的镜头上才划得来。
- 5.3 打开 5.1.2 存的文件、跑模板都没有报错，Alembic 和缓存修改器正常。
- 已知问题：Alembic 读不了中文路径，已经绕开；样板 A 存盘前后画面不一样，见第 1 节。

后台测试：`bash D:/render_tmp/fr_tools/run_tests2.sh`，日志和结果在 `G:/cdk20/work/speedtest/`（`times.txt` 记每项开始时间，`<方式>/_fast_render.json` 是数字，`A_old_*.log`、`B.log`…`G.log` 是日志）。它会等机器上的 Blender 不超过 1 个才开下一项，并重测 B–G。

暂定建议：以后一律用 `fast_render.py` 整段渲，不再在脚本里逐帧调 `render(write_still)`；默认用 Cycles 正式档，版本先用 5.1.2，等 B 和 C 在显卡空闲时重测完再决定换不换 5.3；EEVEE 等看过画质再说。
