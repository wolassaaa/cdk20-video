# GPU 迁移普查（11-24 夜）

HKBU SCIE1007 课程作业的科普视频。这一步：把制作流程里还在 CPU 上、能挪到显卡（RTX 5080：3D/CUDA 核心、NVDEC、NVENC 各自独立）的环节找出来，能挪的挪过去。标准（导演原话）：实测更快、画面或机检结论不差（SSIM ≥ 0.995 或逐位相同、帧数一致、色彩标记一致、机检结论一致）就切成默认；变慢或变差就不切，写明原因。

机器：AMD Ryzen 7 8845H（8 核 16 线程，带 780M 核显）+ RTX 5080 16 GB，系统内存 28 GB（常只剩 4–8 GB）。测的时候队列里有 2 个 Blender 在搭场景/渲染，CPU 本来就忙，数字都是"忙机"下的。

不在本次范围（别人在做或已做）：拼片 build_v10.py（已有 CDK20_GPU_DEC=1）、出镜三维逐帧合成 shot_oncam.py comp → comp_gpu.py（另一位在搬 torch CUDA）。

## 二、Remotion 渲染（已切）

- 显卡检测：用 Remotion 自带的 headless Chromium 开页面读 WebGL 渲染器字符串。

  | --gl | 实际用的 |
  |---|---|
  | 不写（默认） | SwiftShader（CPU 软件渲染） |
  | **angle**（现用） | **ANGLE → NVIDIA GeForce RTX 5080，D3D11** |
  | vulkan | ANGLE → NVIDIA RTX 5080，Vulkan |
  | angle-egl / egl / swiftshader | Microsoft Basic Render Driver（软件） |
  | swangle | SwiftShader |

  机器有 780M 核显，但 angle 选到的是 5080，不用改显卡偏好。
- 并发：`--concurrency` 2 → 6。CPU 是瓶颈（Chromium 排版、JS、JPEG 编码），显卡只占百分之十几。8 不比 6 快，内存却更多。
- 开关：`CDK20_REM_CONC`（b_page.py 读；彩蛋脚本读同名环境变量），=2 即回旧做法。
- 内存：c=6 一个渲染约 3 GB（node + 6 个 chrome-headless-shell 工作集合计，实测 2.5–3.1 GB）。空闲 5 GB 时同时只放 1 个 Remotion，空闲 ≥ 7 GB 放 2 个（队列自动按内存判断）。

## 三、队列并发规矩（已改，_env/queue）

旧：显卡任务（Blender）≤ 2；`remotion`、`ffmpeg` 同时只 1 个；其余不限。
新（11-24，导演定的资源上限）：

- Blender（res=gpu）不变：同时 ≤ 2 个（按 blender.exe 进程数和显卡任务数取大）。
- 其余任务逐个放行，要同时满足：
  - 同类上限：remotion 2、ffmpeg 4、comp 4、cut 1、whisper 1（没列的种类不限个数）；
  - 空闲内存：放行后还剩 ≥ 1 GB。每个任务按 remotion 3 GB、ffmpeg/comp 0.9 GB、cut 2 GB、whisper 3 GB、其他 0.5 GB 预扣；起来不到 2 分钟的任务内存还没涨上来，按满额预扣；
  - 显存：nvidia-smi 已用 + 本任务（显卡合成类约 0.4 GB）≤ 12 GB（16 GB 里留 4 GB 给导演）；
  - NVENC：同时编码会话 ≤ 8（按 nvidia-smi 会话数和在跑的编码类任务数取大）。
- 回旧规矩：环境变量 `QUEUE_OLD_SLOTS=1` 启动 runner。

## 四、出镜三维搭场景缓存

- 做法：`inserts/build_cache.py`。run_oncam.sh 的 build 步骤先算哈希：shot_oncam.py 和它 import 的本目录模块（递归，comp_gpu 除外）、映射/resolve.py、kit_*.json、该段 keys / oncam json、工作目录 light.json / light_fit.json、G 盘 kit/ 全部文件（大小+修改时间）、人像帧目录（张数+最新修改时间）、CDK20_PJSON、采样数、Blender 路径。和上次搭完记下的一样，且 scene.blend / cam.json / check.json 之后没被改过（calib、rimcal 会改场景），就不开 Blender；否则照旧重搭，搭完记哈希。
- 开关：`CDK20_BUILD_CACHE`（1 用缓存，0 每次重搭）。默认值等第六节验证过了才改成 1。
- 验证：队列任务 gmig_build509（5-09 搭两遍，各渲 10 帧 1080p 比对，cam.json/check.json 比字节，原文件先备份后还原）。结果见第六节。

## 五、守卫（cdk20_guard/guard.py）没改

守卫限的是"同时最多 2 个 blender.exe"，搭场景阶段也算一个。实测两个 Blender 都在渲染时显存共 7.7 GB（含桌面），一个渲染进程约 3–3.5 GB，12 GB 预算下最多再放 1 个渲染进程。但守卫和 run_oncam.sh 的 busy() 都只按进程数数，分不出"搭场景"和"渲染"；要分得改命令行识别（`-- build` 参数）或按显存数，误判会把第三个渲染放进来顶爆显存。没把握，**不动守卫**，交总管定。搭场景缓存命中时本来就不开 Blender，等于少占一个名额。
